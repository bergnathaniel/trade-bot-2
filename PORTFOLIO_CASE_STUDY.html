A trading system that worked, and a trade that didn't

I spent August building an automated crypto trading stack — six strategies, real-time on-chain data, a backtester that runs the production code. It lost money, decisively and cheaply. This is the honest account: what got built, why the trade has no edge, and what the build proves I can do.

Context

The goal was income. The result was a conclusion.

The premise: retail crypto markets move fast and inefficiently, so a fast, disciplined, fee-aware bot might extract a small steady edge. I built the whole apparatus to test that properly rather than guess — paper-trading by default, one real-money session, every strategy measured against buying and holding.

The verdict came back clean and negative. Not “needs tuning” — structurally negative: at the position sizes a retail account actually runs, fixed transaction costs, slippage on thin liquidity, and adverse selection against faster bots exceed any edge these signals carry. The cost of learning that first-hand was $3.48.

System

Six strategies on one execution and risk core

Each bot is a separate loop with its own logs, state file, and bankroll cap, so they run concurrently against a shared wallet without touching each other's positions.

bot.py
Graduated-token scalper. Subscribes to the pump.fun migration websocket, filters on liquidity / holders / authority state, exits once profit clears round-trip cost.
insider_bot.py
Smart-money copy-trader. Mines early buyers of past 3×+ winners, scores wallets on early-win count, hit rate, recency and wash-trading shape, then copies live buys with conviction-weighted sizing.
newcoin_bot.py
Meme-coin momentum. Seven-stage gate — liquidity/cap band → SOL regime filter → on-chain rug screen → live price-action classifier (breakout / pullback) → edge-vs-cost gate → optional learned scorer → two-stage trailing exit.
alpha_bot.py
Push-based real-time copy. Helius websocket + X filtered stream + local webhook, fused on one async queue, signal-to-decision in under a second.
momentum_basket.py
20-day trend basket. BTC / ETH / SOL held when price is above its 20-day-ago close, weighted inversely to recent volatility, rebalanced on drift. The one approach that beat buy-and-hold in backtest.
dca_bot.py
Dollar-cost-averaging baseline. The control group — a fixed schedule with no timing, to measure everything else against.

Shared core

executors.py (Jupiter swap: order + execute, signed with solders) · wallet.py (BIP39 mnemonic → keypair, stdlib only) · rug_screen.py · per-strategy config with hard risk limits · a backtester per strategy.

Architecture

The parts that outlast the trade

Real-time ingestion

Per-wallet Helius logsSubscribe websockets; the pump.fun migration feed; an X API v2 filtered stream with programmatic rule management; a local HTTP webhook endpoint. Multiple sources normalise onto a single async queue with de-duplication and a “first source wins” / “N sources confirm” fusion switch. Against live, partly-undocumented third-party APIs, with schemas verified against real traffic.

On-chain analysis — the rug screen

Eight hard checks, any one fails the token: mint authority live, freeze authority live, LP not locked or burned, liquidity below floor, single-wallet or top-10 holder concentration (read on-chain via getTokenLargestAccounts), gradual LP drain over the last hour, serial-deployer history, honeypot-shaped price impact on a probe sell. Softer signals dock a graded score rather than hard-failing; unverifiable data becomes a warning, never a silent pass.

Backtesting that tests the real code

The backtester replays the actual production classifier and exit logic over historical 5-minute OHLCV — not a re-implementation — with a cost and slippage model and a strict in-sample / out-of-sample split. It is what turned “breakout looks great” (in-sample +40%/trade) into “breakout is noise” (out-of-sample net loss) before any real money was involved.

Risk framework

Per-strategy bankroll caps, per-trade position caps, a daily-max-loss circuit breaker, a slippage-rejection guard, and every skipped candidate logged with the reason it was skipped. Live mode refuses to start without a typed confirmation phrase. Mnemonic derivation and the logistic-regression scorer are both hand-written on the standard library — four third-party packages in the whole system.

Wins get taken early at a fixed target; losses run to a stop that slips through thin liquidity. The hit rate is positive and the expectancy is −$0.64 per trade. In the copy strategies the failure mode is different but rhymes: by the time a retail order lands, the wallets worth copying have been front-run by faster bots — every dry-run candidate came back too_crowded.

The system did its job. It ingested, screened, sized, executed and logged exactly as designed — and used all of that to demonstrate, cheaply and repeatably, that there is no edge here to capture.

Evidence

What the build demonstrates

The trading thesis failed. These capabilities are what remain, and they transfer directly to production data and backend work:

  • Async, multi-source real-time pipelines against live third-party APIs — websockets, filtered streams, webhooks, fused and de-duplicated on one queue with sub-second latency.
  • On-chain data analysis and fraud heuristics on Solana — authority state, holder concentration, liquidity forensics, honeypot detection, graded scoring with explicit handling of unverifiable data.
  • Backtesting infrastructure that exercises real code paths, models costs, and enforces out-of-sample discipline — built to disprove its own strategies, and did.
  • Risk and safety engineering — layered limits, circuit breakers, fail-closed defaults, fully auditable skip logging.
  • Dependency restraint — cryptographic key derivation and a linear model written on the standard library; four external packages total.
  • Calling a result — recognising when a negative finding is conclusive, and writing it down instead of tuning forever.
